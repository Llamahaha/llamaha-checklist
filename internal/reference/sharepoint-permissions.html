SharePoint Permissions

Practical troubleshooting flow for SharePoint access tickets, sharing links, group membership, external access, and OneDrive confusion.

Overview

What usually breaks

Plain-English model

SharePoint access may come from site permissions, Microsoft 365 group membership, SharePoint groups, direct item permissions, sharing links, or inherited permissions. Most tickets are really a mismatch between where the user thinks access comes from and where it actually comes from.

Common symptoms

  • User can open the site but not a folder or file.
  • User has a link, but the link says access is denied or requests approval.
  • Owner added a user to a Microsoft 365 group, but access has not appeared yet.
  • External guest can authenticate but still cannot open the item.
  • User says "SharePoint" but the item is actually in someone's OneDrive.

Fast Checks

Find the access path

Confirm location

  • Collect the exact URL. Identify whether it is a SharePoint site/library path or a OneDrive path.
  • Confirm site name, library, folder, file, and whether the user needs read, edit, sync, or owner access.
  • Check whether the item inherits permissions or has unique permissions.
  • Ask whether access should be temporary, permanent, internal-only, or external.

Verify effective access

  • Use site permissions, advanced permissions, or "Manage access" on the item to see direct users, groups, and links.
  • Check Microsoft 365 group membership for team-connected sites.
  • Check SharePoint Owners, Members, and Visitors groups for classic or permission-managed sites.
  • Inspect sharing links. A link can grant access even when site membership looks wrong.
  • Give Entra ID and SharePoint time to reflect membership changes before declaring the change failed.

Warning before changing permissions

Do not break inheritance, delete sharing links, or add broad groups such as Everyone except external users unless the site owner approves the access model and business impact.

Fix Steps

Common permission paths

Site permissions

  1. Confirm the user should have access to the whole site.
  2. Add the user to the correct site group or Microsoft 365 group instead of granting one-off item permissions when possible.
  3. Ask the user to test in a private browser window if stale sign-in state is suspected.
  4. Document the group added and the approved permission level.

Direct item permissions

  1. Open Manage access on the file or folder and review direct access.
  2. Check whether inheritance is broken and whether another group already has the needed access.
  3. If approved, add the user or group at the narrowest scope that matches the business request.
  4. Record whether permissions are inherited, unique, or granted by link.

Sharing links

  1. Identify link type: specific people, people in organization, existing access, or anonymous/anyone if allowed.
  2. Confirm the recipient is using the same email address that received the link.
  3. Remove or recreate only the problem link when approved; avoid changing all links as a first move.
  4. If "existing access" fails, the user still needs actual permission somewhere else.

External sharing

  1. Check tenant-level sharing settings, site-level sharing settings, and whether guest access is allowed for the domain.
  2. Confirm whether a guest object exists in Entra ID and whether the external user has accepted the invite or one-time passcode flow.
  3. Have the guest test with the exact invited email address, not an alias or personal Microsoft account unless that is the invited identity.
  4. Escalate policy conflicts instead of weakening tenant sharing settings in a live ticket.

Ticket Notes

Common notes to capture

Use this format

  • Requested access: <read/edit/owner/sync> for <site/library/folder/file>.
  • Approved by: <SITE_OWNER_OR_MANAGER>.
  • Access source checked: site group, Microsoft 365 group, direct permission, sharing link, or guest access.
  • Change made: <GROUP_OR_LINK_CHANGED>. No broad permission change made without approval.
  • User test result: successful, still pending propagation, or escalation required.

Escalation criteria

  • External sharing policy needs tenant or site-level change.
  • Permission inheritance is heavily broken and needs design cleanup.
  • Legal, HR, finance, or sensitive project data is involved.
  • Access differs between web, Teams, OneDrive sync, and Office apps after sign-out/sign-in testing.
  • Owner approval is unclear or conflicting.

What To Gather Before Escalation

Evidence package

Collect

  • Exact URL, affected user email, required permission level, and business approver.
  • Screenshot of the access denied message or sharing prompt.
  • Screenshot or notes showing current site/group/direct/link access.
  • Whether the item is SharePoint or OneDrive and whether it is accessed through Teams, browser, sync client, or Office app.
  • For external users: invited address, guest object status if visible, and tenant/site sharing setting summary.
