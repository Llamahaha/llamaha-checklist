SMTP2GO Setup

Checklist for setting up SMTP relay through SMTP2GO, verifying DNS, testing delivery, and escalating cleanly without exposing credentials.

Overview

When to use SMTP2GO

Good fit

  • Scanners, line-of-business apps, monitoring tools, websites, or devices need authenticated outbound SMTP.
  • Microsoft 365 SMTP AUTH is blocked, unreliable for the device, or not desired for application mail.
  • The sender needs better deliverability visibility than a basic ISP relay provides.

Not a shortcut for

Do not use SMTP2GO to bypass security policy, hide a compromised sender, relay bulk mail without approval, or send from domains that have not been authorized for that customer.

Setup Checklist

Configuration path

Account and sender

  1. Confirm approved customer/domain and approved sending use case.
  2. Create or identify the SMTP2GO account or subaccount using approved MSP process.
  3. Verify the sending domain instead of relying on a single sender when possible.
  4. Create SMTP credentials for the app or device. Store the username/password only in approved secret storage.
  5. Record non-secret setup notes in the ticket, including sender address, device/app name, and test recipient.

Typical SMTP settings

Use SMTP2GO's published server settings and the current supported ports from their documentation. Keep placeholders in notes: server <SMTP_SERVER>, port <PORT>, username <SMTP_USERNAME>, sender <FROM_ADDRESS>.

Warning before DNS changes

Check the existing SPF, DKIM, and DMARC posture before editing DNS. Do not replace a working SPF record without reviewing all current senders, and do not lower DMARC protection without approval.

DNS

Records to verify

SPF

  • Confirm the domain has one SPF TXT record, not multiple competing SPF records.
  • Review whether SMTP2GO domain verification uses CNAME records for return-path alignment instead of requiring a direct SPF include.
  • Validate that all approved sending services are still represented after any change.

DKIM

  • Verify the DKIM CNAME/TXT records requested by SMTP2GO have propagated.
  • Confirm the domain shows verified inside SMTP2GO before production testing.
  • If messages show "via" another domain in mail clients, check whether the sender domain is fully verified or only a single address was verified.

DMARC

  • Confirm a DMARC record exists or document why it does not.
  • Check alignment expectations before changing a policy to quarantine or reject.
  • If failures appear, compare the visible From domain, return-path, DKIM domain, and SMTP2GO verification status.

Testing

Validation steps

Test send

  1. Send to an internal recipient and an external test mailbox.
  2. Confirm the message arrives, does not land in junk, and has the expected From and Reply-To.
  3. Review SMTP2GO activity/logs for accepted, rejected, bounced, or deferred messages.
  4. Open message headers and check SPF/DKIM/DMARC results where possible.
  5. Document the exact device/app settings without including the password.

Common failure points

  • Wrong SMTP username or password, copied with a trailing space.
  • Device cannot negotiate the selected TLS mode or port.
  • Firewall blocks outbound SMTP ports.
  • Sender domain not verified, From address does not match the authorized domain, or DNS has not propagated.
  • Application sends a malformed From address, missing authentication, or a recipient blocked by policy.

What To Gather Before Escalation

Evidence package

Collect

  • Device/app name, sender address, recipient address, timestamp, and timezone.
  • SMTP server, port, encryption mode, and authentication username only. Do not include passwords.
  • Screenshots of SMTP2GO activity, verification status, and the application error.
  • DNS screenshots or output showing SPF/DKIM/DMARC records.
  • Full bounce or SMTP error text, with sensitive addresses redacted if needed.
